# draft ドキュメント同期

PLAN.md / SPEC.md / TODO.md / KNOWLEDGE.md を、このセッションの会話内容を参照して最新化する。

## フォルダパスの特定

引数でフォルダパスが渡されていればそれを使う。渡されていない場合は以下の順で自動特定する：

1. **会話で言及されたパス**: セッション中に `_draft` プレフィックスのフォルダに触れていればそれを使う
2. **セッション中に読み書きしたファイル**: PLAN.md / TODO.md 等を操作していたフォルダ
3. **直近の _draft フォルダ**: ワークスペースルート直下で `_draft` プレフィックスのフォルダを `ls -t` で検索し、最新の作業ディレクトリを候補にする

候補が見つかったらユーザーに確認する：「📁 `_draft/2026-03-05_freee申請/` を更新しますか？」
候補がなければフォルダパスを聞く。

## 実行手順

1. フォルダパスを特定（上記ルール）
2. 4ファイルの存在を確認
3. 存在しないファイルの扱い:
   - PLAN.md / TODO.md / KNOWLEDGE.md → テンプレートから新規作成（`/draft:init` と同じ）
   - SPEC.md → 設計の壁打ちが発生しているタスクなら作成。申請・手続き・タスク管理系はスキップ
4. 既存ファイルを読み込む
5. **セッションの会話内容**と照らして、追記・更新が必要な箇所を特定
6. 更新を実行し、結果を報告
7. **4 ファイル以外の追加ファイル提案**: 会話内容を見て、_draft 内に新規追加すべきファイルがあるか判定（下記「## 4 ファイル以外の追加ファイル提案」参照）

## 更新ルール

### PLAN.md

- ユーザーの言葉をそのまま保持する。勝手に整形・要約しない
- 会話でユーザーが背景や動機を語っていたら、その言葉をそのまま追記する
- 既存の記述は削除・書き換えしない（追記のみ）

### SPEC.md

- 会話で決まった仕様や壁打ちの結果を反映する
- 未確定事項は `> ⚠️ 未確定:` で明示する
- 前回との差分がわかるよう、新しい決定事項を追記する
- **SPEC.md が不要なケース**（申請・手続き・タスク管理系など、設計の壁打ちがない作業）はスキップしてよい。
  存在しないファイルを無理に作らない。報告では「なし（スキップ）」と記載する。

### TODO.md

- 会話で出てきたタスクをチェックリストに追加する
- 完了したタスクは `- [x]` に更新する
- 新しく見えてきたタスクがあれば追加する

### KNOWLEDGE.md

- セッション中にハマったこと、発見したことを追記する
- 既存の記載と重複しないよう確認してから追記する

## _draft 内の非 draft ファイル整理

draft ドキュメント（PLAN/SPEC/TODO/KNOWLEDGE）以外のファイルがディレクトリ内にある場合、以下の手順で整理する。

### 判断基準

各ファイルを読み、セッションの会話内容と照合して以下を判断する:

| 判断 | 条件 | アクション |
|------|------|-----------|
| **維持** | 独立した素材として価値がある（観察ログ、分析結果、外部向け資料等） | そのまま残す。必要なら会話内容で更新 |
| **統合** | 内容が draft ドキュメントと重複している | 重複部分を draft 側に統合済みか確認し、統合済みなら削除 |
| **削除** | 空ファイル、探索途中で却下されたもの、git 履歴で復元可能なもの | 削除する |

### ディレクトリ構造の見直し（毎回実行）

ファイルが増減するとディレクトリの最適な形は変わる。**毎回の sync 実行時に現在の構造が最適かを見直す。**

#### 分類ルール

| 種別 | 置き場所 | 例 |
|------|----------|-----|
| draft ドキュメント | ルート直下（固定） | PLAN.md, TODO.md, KNOWLEDGE.md |
| 設計・アーキテクチャ系 | ルート直下（参照頻度が高い） | 記憶システム設計.md |
| output 系（生成物・成果物） | `output/` | 観察ログ、分析結果、戦略メモ |
| source 系（入力素材・文字起こし） | `source/` | 文字起こし、参考記事、元データ |

#### 見直しの判断フロー

1. `ls -R` でディレクトリ全体（サブディレクトリ含む）を把握
2. 以下をチェック:
   - **まとめるべき**: ルート直下の同種ファイルが 3〜4 件以上 → サブディレクトリ化
   - **昇格すべき**: サブディレクトリ内のファイルが 1 件だけ → ルート直下に戻す（ディレクトリ削除）
   - **移動すべき**: セッション中に性質が変わったファイル（例: output だったが設計書に進化）→ 適切な場所に移動
   - **空ディレクトリ**: 中身がなくなったサブディレクトリ → 削除
3. 変更がある場合は実行し、報告に含める

#### 例

```
# ファイルが増えてきた → output/ にまとめる
_draft/xxx/
├── PLAN.md
├── 設計書.md
└── output/
    ├── 観察ログ.md
    ├── パターン分析.md
    └── 戦略メモ.md

# output/ が 1 件だけになった → ルート直下に戻す
_draft/xxx/
├── PLAN.md
├── 設計書.md
└── 戦略メモ.md         # output/ から昇格
```

### ファイルリネーム（内容がわかる名前にする）

draft ドキュメント以外の**ドキュメントファイル**について、ファイル名だけで内容が推測できるかを確認し、必要ならリネームを提案する。

#### 対象

- `.md` などのドキュメントファイル全般（source/ output/ ルート直下 問わず）

#### 対象外

- PLAN.md / SPEC.md / TODO.md / KNOWLEDGE.md（draft 固定名）
- プログラムファイル（.py, .js, .ts, .sh, .json 等）— インポートパスが壊れるため

#### 命名規則

`YYYY-MM-DD_主題_補足.md`

| 要素 | ルール | 例 |
|------|--------|-----|
| 日付 | そのファイルの作成日 or 内容の日付。不明なら省略可 | `2026-03-27` |
| 主題 | ファイルの核心を 5-15 文字で | `全社会_観察ログ` |
| 補足 | 主題だけで区別がつかない場合に追加。なくてもよい | `活用スタイル5類型` |

#### 判断基準

- **リネーム不要**: 既に日付+主題で十分わかる（例: `2026-03-27_全社会_観察ログ.md`）
- **リネーム推奨**: 主題が抽象的で中身を開かないとわからない（例: `メモ.md`, `調査.md`）
- **リネーム推奨**: 日付がなく、いつの情報か不明（例: `軍学パターン.md` → `2026-03-27_軍学パターン_活用スタイル5類型.md`）

#### 実行ルール

- リネーム候補を一覧で提示し、ユーザー確認後に実行する（勝手にリネームしない）
- 1 ファイルも候補がなければこのステップはスキップ

### 実行手順

1. `ls -R` でディレクトリ全体のファイルを列挙
2. draft ドキュメント（PLAN.md / SPEC.md / TODO.md / KNOWLEDGE.md）を除外
3. 残ったファイルについて、セッション会話を参照して判断基準（維持/統合/削除）を適用
4. ファイルリネームの候補を提示（上記ルール）
5. ディレクトリ構造の見直しを実行（まとめる/昇格/移動/空削除）
6. 整理結果を報告に含める

### 報告に追記する内容

```
📄 非 draft ファイル:
- [ファイル名]: [維持 / リネーム: 旧名→新名 / 統合→削除 / 削除（空）]
```

## 4 ファイル以外の追加ファイル提案

旧 `session:freeze` の代替機能。セッション中に **失われると作業再現ができない情報** が発生したとき、PLAN/SPEC/TODO/KNOWLEDGE のどこにも入らない場合、_draft フォルダ内に追加ファイルとして残す提案を出す。

該当候補があればユーザーに提案する（**勝手に作らない**）。**0 件ならセクションごと省略**。

### 判定基準

以下のどちらかに該当する情報が会話中にあるか:

- **強い基準**: 失われると作業再現ができない（一次資料・出典・採用却下の根拠・他では参照できない比較等）
- **弱い基準**: あったら便利（URL が 3 つ以上出た / 候補比較が会話に展開された / 結論を 1 ページに要約したい等）

### 該当しうるファイル例（網羅ではなく着想用）

| ファイル名（例） | 内容 | 使い所 |
|---|---|---|
| `REPORT.md` | このタスクの結論を 1 ページ要約 | 後で buildin / Notion publish する時の親ページ |
| `refs.md` | 引用 URL・関連資料のリンク集 | 出典を辿りたい時 |
| `compare.md` | 候補の比較表 | PLAN.md 内に書くと肥大化する場合の分離 |
| `decisions.md` | 採用 / 却下した選択肢の記録（ADR 的） | 「なぜこの案にしたか」を後で参照 |
| `source/transcript.md` | 文字起こし・議事録抜粋 | 一次資料 |
| `output/<doc>.md` | 配布用のドラフト・成果物 | 完成版を 4 ファイルから分離 |

例にない種類のファイルでも、判定基準に該当すれば提案してよい。

### 提案フォーマット

報告の末尾に **独立ブロック** として追加:

```
💡 こういうファイルも作っておくと良いかも:
- REPORT.md: [1 行で何を入れるか]
- compare.md: [1 行で何を入れるか]
```

ユーザーが「お願い」「やって」等で明示反応したら作る。反応がなければ作らない。

## 報告フォーマット

```
📁 [フォルダパス]
- PLAN.md: [新規作成 / 更新: 背景を追記 / 変更なし]
- SPEC.md: [新規作成 / 更新: 仕様概要を追記 / 変更なし / なし（スキップ）]
- TODO.md: [新規作成 / 更新: タスク3件追加 / 変更なし]
- KNOWLEDGE.md: [新規作成 / 更新: ハマりポイント1件追記 / 変更なし]
📄 非 draft ファイル:
- [ファイル名]: [維持 / 更新 / 統合→削除 / 削除（空）]

💡 こういうファイルも作っておくと良いかも（該当時のみ表示・0 件なら省略）:
- [ファイル名]: [1 行で何を入れるか]
```
